 # Scenario 1: Encoded PowerShell Execution

| Attribute | Details |
|---|---|
| **MITRE ATT&CK** | [T1059.001 – PowerShell](https://attack.mitre.org/techniques/T1059/001/) |
| **Tactic** | Execution |
| **Platform** | Windows 11 |
| **SIEM** | Wazuh 4.14.10 |
| **Endpoint** | Martha (Agent ID: 002) |
| **Detection type** | Built-in and custom detection |
| **Status** | Custom detection validated for tested execution contexts |

## 1. Objective

Investigate how encoded PowerShell commands can be used to execute scripts while making their contents less immediately readable during an initial inspection.

The objectives were to:

- Simulate encoded PowerShell execution safely.
- Identify the Windows telemetry generated by the activity.
- Evaluate Wazuh's existing detection coverage.
- Identify limitations in the built-in detection.
- Develop and validate a complementary custom detection rule.

## 2. MITRE ATT&CK context

**T1059.001 – PowerShell**

PowerShell is a legitimate Windows administration tool that attackers may abuse to execute commands and scripts.

Attackers can encode PowerShell commands using Base64 and pass them through the `-EncodedCommand` parameter. This can make the command less obvious during an initial inspection of process command-line data.

Encoding is not encryption, and encoded PowerShell is not inherently malicious. Legitimate administrative activity can also use this functionality.

## 4. Attack simulation

A harmless PowerShell command was created, encoded using Base64 and executed.

Original payload:

```powershell
$payload = "Write-Output 'WAZUH-LAB-T1059.001'; Get-Date"
```

Encoding:

```powershell
$encoded = [Convert]::ToBase64String(
    [Text.Encoding]::Unicode.GetBytes($payload)
)
```

Execution:

```powershell
powershell.exe -NoProfile -EncodedCommand $encoded
```

The command successfully printed the lab marker and current date.

A second execution was initiated from `cmd.exe` to examine whether Wazuh's detection coverage depended on the parent process.

## 5. Telemetry investigation

Two Windows event sources provided useful evidence.

### 5.1 Sysmon Event ID 1 – Process Creation

Sysmon Event ID 1 records process creation activity.

The collected event contained:

- **Image:** `C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe`
- **Command line:** Included `-NoProfile -EncodedCommand` and the encoded payload.
- **Parent image:** Identified the process that launched PowerShell.
- **User:** `CYBERLAB\Administrator`
- **Process ID:** Recorded by Sysmon.
- **Hashes:** Recorded for the executable.

This event established that PowerShell was launched with an encoded-command parameter.

### 5.2 PowerShell Event ID 4104 – Script Block Logging

## 6. Built-in Wazuh detection analysis

Wazuh generated an alert using built-in rule **92057**.

| Attribute | Value |
|---|---|
| Rule ID | 92057 |
| Severity level | 12 |
| Description | Powershell.exe spawned a powershell process which executed a base64 encoded command |
| MITRE ATT&CK | T1059.001 |

The rule checks for:

1. A parent process image of `powershell.exe`.
2. An encoded PowerShell parameter in the process command line.

The built-in rule successfully detected the execution initiated by another PowerShell process.

### Identified limitation

The rule's parent-process condition restricts its coverage.

To investigate this limitation, the encoded PowerShell command was executed from `cmd.exe`.

In this test, built-in rule 92057 did not trigger.

This demonstrated that the built-in rule did not cover the tested CMD-launched execution.

## 7. Custom detection development

To address the identified coverage gap, custom rule **100100** was added to Wazuh's `local_rules.xml`.

```xml
<rule id="100100" level="5">
    <if_sid>61603</if_sid>
    <field name="win.eventdata.commandLine" type="pcre2">(?i)-EncodedCommand(\s|$)</field>
    <description>PowerShell process launched with an encoded command</description>
    <mitre>
      <id>T1059.001</id>
    </mitre>
    <group>powershell,process_creation,</group>
</rule>
```

### Rule explanation

- **Rule ID 100100:** Identifies the custom detection.
- **Level 5:** Assigns the alert a severity level of 5.
- **`if_sid 61603`:** Requires the event to match Wazuh's Sysmon process-creation classification rule.
- **Command-line field:** Examines the process command line.
- **`(?i)`:** Makes the matching case-insensitive.
- **`-EncodedCommand(\s|$)`:** Matches the full encoded-command parameter followed by whitespace or the end of the command line.
- **MITRE mapping:** Associates the detection with T1059.001.

Unlike rule 92057, the custom rule does not require a specific parent process.

It therefore provides broader coverage for the tested execution contexts.

## 8. Detection validation

The custom rule was tested against actual Windows telemetry collected by Wazuh.

| Test | Parent process | Built-in 92057 | Custom 100100 |
|---|---|---|---|
| Encoded PowerShell | PowerShell | Triggered | Triggered |
| Encoded PowerShell | CMD | Did not trigger | Triggered |

The CMD-launched execution successfully generated an alert for custom rule 100100.

The alert included the encoded-command parameter and identified `cmd.exe` as the parent process.

This confirmed that the custom rule detected the tested execution that the built-in rule missed.

## 9. Findings and limitations

The investigation established that:

1. Sysmon Event ID 1 provided process-creation evidence, including the command line and parent process.
2. PowerShell Event ID 4104 exposed the decoded script content.
3. Built-in rule 92057 detected the tested PowerShell-parent execution.
4. The built-in rule did not detect the tested CMD-parent execution.
5. Custom rule 100100 detected both tested execution contexts.

### Limitations

- The custom rule currently matches the full `-EncodedCommand` parameter only.
- Abbreviated parameter forms have not been tested.
- Benign negative testing remains outstanding.
- An encoded PowerShell command is a suspicious indicator, not proof of malicious activity.

## 10. Conclusion

This investigation demonstrated how to analyze encoded PowerShell execution using Windows endpoint telemetry and Wazuh.

The built-in detection provided useful coverage but had a limitation caused by its parent-process requirement.

A complementary custom rule was developed and validated against two execution contexts, including a CMD-launched execution that the built-in rule did not detect.

The scenario demonstrates the importance of evaluating existing SIEM detection logic, identifying coverage gaps, and developing additional detection rules where they provide meaningful value.

**Final status:** Custom detection validated for the two tested execution contexts. Benign negative testing and abbreviated parameter testing remain outstanding.
